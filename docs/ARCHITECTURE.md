# 架构审查与本轮整理（2026-10-20）

目标是让维护者通过少量明确的 Interface 使用 Module，由 Module 持有任务和状态的不变量；不按文件行数拆分，也不建立全项目通用任务框架。领域用语见 ../CONTEXT.md。

## Standards

审查固定范围 `git diff dad3cb7...2a3371a`，即 preview.5 后的项目树路径操作与本地更改刷新反馈。依据 AGENTS.md、REBASED-REFERENCE.md；仓库无 issue tracker 配置，需求采用功能实现记录，未声称查阅外部 issue。

未发现明确违反项目约定的新增功能。两个架构判断：LocalView 直接维护查询、取消、排队、提示等成组状态；同时负责提交执行报告解释和树渲染，职责容易相互影响。均为重构机会，不是凭字段数量判定的功能缺陷。

## Spec

发现一项性能回归：事件即时分发后 Documents::observe_disk 对所有打开文档检查 stamp，无关事件也会触发磁盘访问；同一计时器还被每个事件重置。修复为受影响路径立即检查、全体打开文档独立每两秒兜底，连续事件不加速或推迟此周期。30 秒仓库补偿仍仅用于 UNC／监听不可用等既有情况。

审查统计：Standards 无硬问题、两项架构判断；Spec 一项性能回归。路径菜单捕获点击时的路径，树重排不会换对象，保留此行为。

## 已落实的 Module

- `changes_refresh::ChangesRefresh`：具体的本地更改查询 Module。Interface 是 request、只读查询状态与 Started／Loaded／Failed 事件；Implementation 持有真实 Git 查询、取消令牌、一次运行加一次合并请求、300ms 延迟反馈和任务释放。LocalView 保有树模型、提交范围、草稿与写操作，不再直接维护查询任务的多个开关。
- `worktree_events::Schedule`：独立的打开文档检查和仓库补偿期限。Interface 接收当前时间与事件批次，产生本次检查决定；不查询 Git，不把普通定时检查转为全仓刷新。
- `Documents::observe_disk`：把事件影响范围与周期检查明确区分。只有命中事件或到期兜底的文档才启动 IO，继续由共享文档保护未保存草稿与迟到结果。

ChangesRefresh 的加载器是内部测试 seam：生产 Adapter 使用真实 Git，测试 Adapter 使用受控完成时机。没有将这套机制泛化到所有后台查询；项目树的分页、Log 的引用查询、远端检查各自有不同生命周期。删除该 Module 会把取消、排队和延迟提示复杂度重新散回视图，因此它不是仅转发的封装。

## 后续优先级

1. 本地提交结果的错误解释可单独整理为有界诊断 Module；本轮不改变写操作与恢复语义。
2. Review 的 Log 查询／过滤／分页仍共享较多状态，下一轮应先以查询身份和结果接纳规则建 seam，再移动代码。
3. ProjectView 中项目树与文件 Tab 有独立生命周期，可分离源码文件，但仅移动代码的收益低于上述状态所有权整理。

暂不引入事件总线、依赖注入框架或全仓命名重写。已知 Diff `releasing_diff_clears_padding_from_retained_source` 基线失败不混入这轮刷新重构。

206 项库测试、2 项文件监听集成测试及 38 项桌面测试通过；上述已知 Diff 基线失败仍单独排除。Windows release 构建和原生慢刷新验证通过：更新提示出现／消失不挪动文件行，空闲八秒 status 调用保持 2 次，文件修改后变为 3 次。证据见 `artifacts/refresh-architecture-20261020/`。未测量异机 Windows→WSL 耗时，不能据此声称解决所有刷新性能问题。

## 第二轮：提交反馈解释（2026-10-20）

检查 LocalView 的提交完成路径发现，视图同时理解执行步骤、状态优先级、多个恢复错误和输出长度限制。旧实现先拼接 Git 输出再追加恢复错误，最终从开头截取 32000 个字符；大量 hook 输出可能让 index 恢复失败的具体原因完全消失。

新增 `commit_feedback` Module，Interface 为 `from_report(&Report)` 及执行前错误／显式恢复错误的构造入口，输出既有标题键和有界详情。它只处理进程内数据，不需要 I/O Adapter；成功与失败分类继续由 `Report::status` 决定，避免产生第二套状态判定。Implementation 优先保留恢复、记录清理和仓库状态错误，再放最后步骤的输入／进程输出，按 Unicode 字符限制长度并显式标记截断。流本身已截断时也保留标记。视图负责显示与成功后的草稿清理，不再解释 Git Report 的字段。

保留具体 Commit Module，未扩展成所有 Git 操作共用诊断框架；各操作的成功和部分完成语义不同。Log 查询与 ProjectView 拆分仍是后续候选，不仅为减少行数做迁移。

本轮验证：3 项新 Module 单测、33 项 Git 集成测试、38 项桌面测试通过（既有 Diff 基线失败继续排除）。Windows release 与原生启动通过；自动化前台焦点／输入受限，提交失败弹窗交互待手工验收，未宣称已覆盖。

## 第三轮：文档保存协议与统一格式（2026-10-22）

检查基线 `611f9e4`，使用 codebase-design 的深模块与状态所有权准则，并用
领域词汇区分草稿和磁盘错误。这是热点检查，不宣称已穷尽所有模块或性能问题。

发现与处理：

1. `Documents` 用四个编号字段承载注册表、锁、草稿保留和回调；`Review` 在保存屏障中
   直接遍历每份文档，重复解释 saving/pending/error。刚修复的外部删除问题说明此处
   的规则容易泄漏。改为命名字段，`save_all` 返回持有参与文档的 `SaveBatch`；
   调用方只接收 Saving、Ready 或 Blocked。等待节拍、窗口回调和操作锁继续归 Review，
   文档模块只负责文档语义，不引入全项目操作框架。已有真实关闭／保存回归通过同一接口
   验证，不增加只校验新字段布局的测试。
2. `Review` 仍集中维护历史查询、图投影、选中提交详情、导航和分页状态；
   `ui/log_history.rs` 虽已拆文件，仍是对同一个 Review 的 impl。它是下一处值得深化的
   模块，不能把文件拆分算成状态隔离完成。下一轮应以请求身份与迟到结果拒绝规则切入，
   同时覆盖过滤切换、分页和刷新保留选择；本轮没有改动这些行为。
3. 多数自有 Rust 文件混合压缩单行写法，缺少格式门槛。本轮建立 rustfmt、EditorConfig
   和固定工具链，格式化包内自有代码及测试；CI 在核心测试前检查格式。
   `tests/editor_row_gaps.rs` 跨路径引用第三方文件，显式跳过递归格式化，vendor 保持不变。
   全仓格式化造成行数增加不代表职责变多，不以固定行数阈值强迫拆分。

模块依赖：SaveBatch 仅使用进程内 GPUI 文档实体；没有外部 I/O adapter 或新依赖。
其 Interface 隐藏强引用保留与保存状态优先级；删除它会把判断规则重新放回 Review。
保留 Documents 的现有共享引用方式和弱引用回调，避免引入闭环引用。
规范单一入口为 CONTRIBUTING.md，AGENTS.md 只保留入口与必跑格式检查。

验证：自有包格式检查通过，vendor 无差异；核心测试 601 项通过，相关桌面回归
13 项通过，最终保存屏障 3 项在消除 must_use 编译警告后重跑通过。核心 Clippy

## 第四轮：主 Log 查询生命周期（2026-10-22）

沿用 codebase-design 的状态所有权准则，检查 Review 的刷新、单选／多选详情、
定位提交以及进入 Diff 的取消路径。原有 generation、token、task、busy、
history_loading 分散维护；导航手动替换其中部分字段，reset_job 的取消还会留下
加载标志。代码拆成多个 impl 文件没有解决该问题。

新增私有 `ui::log_query::Query`，以 History／Details／Navigation 区分工作类型，
begin、track、finish、cancel 管理请求身份、任务与取消；busy/history_loading
从同一个 active 状态派生。调用方必须先 finish 成功再接纳成功或失败结果。
重复或迟到结果不能关闭新请求的加载反馈；完成后的身份仍供相邻提交菜单核对，
新请求或显式取消后失效。Drop 取消底层 Git token；缓存命中和空选择同步完成。
请求取消与界面提示清理分离，后者仍归 Review 的 reset_log_presentation。

本轮也修正进入 Diff 取消 Log 查询后遗留加载状态的路径。实际入口回归覆盖
refresh → activate_diff_tab → refresh，并验证旧完成不能解除新查询的加载状态。
另覆盖缓存命中／空选择、导航与历史替换、销毁取消。没有改变历史的读取规模、
分页固定 tips、过滤算法、选中恢复或滚动锚点；graph 投影任务仍单独管理。
未将新模块推广到 FileHistory、项目树或远端查询，它们有不同的生命周期。

剩余工作：Review 仍持有查询参数、Git 结果装配及多个界面模型。此次只完成请求
生命周期 seam，不宣称整个 Log 已完全独立；后续可沿 history::Window 的输入输出

### 1. Log 页面（已实现并验证）

`ui/log_display::Display` 成为已接纳页面的 owner：一次构造同批提交元数据、
仓库身份、固定 Scope、分页游标、位置与图投影，字段对调用方只读。底层 Entry
拆出的两份只读显示索引由同一次构造产生，不再允许视图分别改写；没有增加历史
加载规模。单仓库构造返回移走 commits 后的主仓库 Snapshot，多仓库构造移走
Window 内的元数据而保留 continuation，不重复保留完整历史。

`Review` 保留用户过滤输入、选择、焦点、滚动和 Query 请求生命周期。单仓库刷新、
项目刷新、定位提交均通过页面接纳入口；计数只读页面 Scope，不再回写查询范围，
“已全部加载”取当前页面而非主仓库 Snapshot。图重投影在 module 内复验 model
身份；单仓库导航也在后台生成属于新页的 model，避免接纳新行后沿用上一页投影。

已有同 hash 不同仓库、过滤／分页、详情、计数及导航测试迁移为替换完整页面，
不再通过制造长度不一致的平行字段来布置状态；缺失行改为页面替换后旧选择失效。
新增入口测试覆盖固定 Scope、主快照不重复保存元数据、跨仓库身份以及旧投影拒绝。
本项验证：177 项桌面测试、10 项关闭 debug assertions 的导航测试通过；Windows
release bins 构建、cargo fmt 和 diff 空白检查通过。原生独立多仓库 fixture
确认父／子仓库详情绑定、12/12 总数、extra 过滤后 1/1、清除后恢复 12/12。
